# Sparse KV Offload 卸载测试脚本

整理日期：2026-10-26。适用于当前工作区的 sparse KV offload 实现。

本文提供启动命令与验证步骤，未在 NPU 上实际执行。命令需要在安装了当前版本 vLLM、vLLM Ascend 和匹配依赖的 Ascend Linux 环境中运行。

## 1. 验证方式

建议先使用单机调试模式验证 LRU、CPU KV 回载和生成结果，再使用 PD 分离模式验证完整卸载与容量收益。

| 模式 | 配置 | 验证目标 |
| --- | --- | --- |
| 单机调试 | `keep_device_kv_cache=true`，不配置 KV connector | 一个服务完成 prefill/decode，验证 offload 功能 |
| PD 分离 | D 设置 `keep_device_kv_cache=false`，配置 P、D 和 proxy | 验证主 KV 卸载、跨节点传输及容量收益 |

单机调试模式仍保留完整 NPU 主 KV cache；decode 会走 CPU KV 池、LRU 与 miss-only H2D，但不能以该模式衡量移除完整 NPU 主 KV cache 带来的容量提升。

当前支持 `lru`（默认）和 `reuse_prioritized_lru` 两种 CPU C++ 淘汰策略。对比测试保持其他配置与输入一致，只切换 `eviction_policy`；新策略可通过 `probation_age` 调整 Miss 的初始年龄。

## 2. 环境检查

当前实现要求：

- 支持 SFA 的稀疏注意力模型，例如 DeepSeek-V3.2；模型配置需要包含 `index_topk`。
- Model Runner V1，不支持 Model Runner V2。
- MemFabric Hybrid 1.2，且包含 `offload` 模块。仓库部署说明要求 NPU driver 25.5.1 或更高版本。
- Clang、OpenMP，以及可编译 torch C++ 扩展的环境。
- 足够的 CPU 内存，用于完整主 KV 池。
- 不启用 context parallel 或 pipeline parallel。
- 主 SFA cache 使用 BF16，关闭 `enable_sparse_sfa_c8`；这与模型权重 W8A8 量化是不同设置。

检查依赖：

```bash
python -c 'from memfabric_hybrid import offload; print("offload import OK")'
clang++ --version
```

仅 import 成功不能替代 MemFabric 运行验证。启动时会编译 `sparse_kv_offload.cpp`，因此还需确保 Clang 和 OpenMP 头文件、链接库可用。

如果按仓库说明安装 MemFabric Hybrid 1.2 到默认目录，可以设置：

```bash
export MEMFABRIC_HYBRID_EXTEND_LIB_PATH=/usr/local/memfabric_hybrid/1.2.0/aarch64-linux/lib64
```

实际安装位置不同则调整路径。

## 3. 单机 eager 功能验证

### 3.1 启动服务

以下以 A3、16 卡、DeepSeek-V3.2-W8A8 为示例。模型路径、TP 和内存配置需按实际机器调整，不能将该模型配置直接照搬到卡数不足的环境。

```bash
export VLLM_USE_V2_MODEL_RUNNER=0

vllm serve /path/to/DeepSeek-V3.2-W8A8 \
    --served-model-name sparse-offload-test \
    --host 0.0.0.0 \
    --port 8000 \
    --tensor-parallel-size 16 \
    --data-parallel-size 1 \
    --enable-expert-parallel \
    --quantization ascend \
    --trust-remote-code \
    --max-model-len 16384 \
    --max-num-seqs 2 \
    --max-num-batched-tokens 4096 \
    --gpu-memory-utilization 0.85 \
    --no-enable-prefix-caching \
    --enforce-eager \
    --additional-config '{
        "enable_sparse_sfa_c8": false,
        "sparse_kv_offload_config": {
            "enabled": true,
            "keep_device_kv_cache": true,
            "topk_buffer_size": 4096,
            "dram_size_per_dp_GB": 128,
            "lru_max_threads": 8
        }
    }'
```

参数说明：

| 参数 | 用途 |
| --- | --- |
| `VLLM_USE_V2_MODEL_RUNNER=0` | 强制使用 Model Runner V1 |
| `keep_device_kv_cache=true` | 支持单机 prefill/decode 调试，无需 KV connector |
| `topk_buffer_size=4096` | 每个 query row 的 resident token 容量，必须不小于模型 `index_topk`，并能被 KV block size 整除 |
| `dram_size_per_dp_GB=128` | 每个 DP 组的 CPU KV 池大小，TP ranks 共享，需要足够主机内存 |
| `lru_max_threads=8` | 每个 Decode Worker 的 CPU LRU 线程上限，实际线程数还受有效行数及 CPU affinity 限制 |
| `--enforce-eager` | 先验证基本功能，再验证图模式 |
| `enable_sparse_sfa_c8=false` | 保持主 SFA cache 为当前支持的 BF16 路径 |

128 GiB 为示例，需结合可用主机内存与启动时估算的 KV 内存调整。若出现以下错误：

```text
Needed dram size (...) GB is larger than user specified dram size (...) GB.
```

可在主机内存允许时增大 `dram_size_per_dp_GB`，或降低 `gpu-memory-utilization` 后重新验证。

### 3.2 发送短请求

服务就绪后，在另一个终端运行：

```bash
curl http://127.0.0.1:8000/v1/completions \
    -H 'Content-Type: application/json' \
    -d '{
        "model": "sparse-offload-test",
        "prompt": "Please explain how an LRU cache works.",
        "max_tokens": 128,
        "temperature": 0
    }'
```

先确认请求可以完成且生成结果正常。该短请求用于服务连通性和基本功能检查。

### 3.3 使用长请求观察跨轮驻留

验证 LRU 跨轮驻留时，使用 token 长度超过 `index_topk`、最好也超过 resident 容量的长 prompt，并生成数百个 token。短上下文可能全部容纳于 resident，难以观察淘汰效果。

本示例中 resident 容量为 4096，可准备约 8192 token 的 prompt，输出 256–512 token。以实际 tokenizer 计数，确保 prompt 与输出总长不超过 `max-model-len=16384`。这只是测试规模建议，不保证特定输入一定产生足够的淘汰或某个命中率。

需要记录：

- 请求是否正常完成，是否出现 KV 地址、复制或 attention 错误。
- 相同模型和输入在关闭 offload 时的生成结果，以及开启 offload 后的精度对照。
- 每轮有效 top-k 数、Miss 数，以及多轮 decode 中的 resident 复用情况。

### 3.4 检查初始化日志

启动日志应包含类似内容：

```text
Sparse KV offload build cpp utils from src: ...
SparseKVOffloadManager start init CPU KV pool ...
Sparse KV offload registered ... layers ...
LRU thread budget: ...
```

这些日志只能证明相关初始化路径被执行，不能证明实际 Hit Rate 或每轮 KV 内容正确。

当前实现没有逐轮 Hit Rate 日志。若需定量验证，应在 C++ 决策输出处汇总有效访问数和 `miss_count`：

```text
Hit Rate = (有效访问数 - Miss 数) / 有效访问数
```

有效访问数为过滤 padding 与无效索引后的访问数量；汇总时明确 layer、query row 和 TP rank 的统计范围，避免将复制的 TP 统计误计为额外访问。不要在每个 token 的热路径逐条打印日志。

## 4. 验证图模式

eager 模式跑通后，从第 3 节命令中删除：

```bash
--enforce-eager
```

并增加：

```bash
--compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}'
```

其他配置先保持一致，重复短请求和长请求，比较生成结果与 decode 延迟。

当前图模式通过 host callback 调用 CPU C++ 做 LRU 决策，再上传拷贝描述符和 `current_slots`。检查图模式结果时，需覆盖多次 replay、请求替换及 batch 大小变化。

## 5. 验证 PD 分离卸载

### 5.1 D 节点配置

以第 3 节的模型配置为基础，在 D 节点将：

```json
"keep_device_kv_cache": false
```

并增加：

```bash
--kv-transfer-config '{
    "kv_connector": "SfaRemoteD2HConnector",
    "kv_role": "kv_consumer",
    "kv_port": 20050,
    "kv_connector_extra_config": {
        "transfer_backend": "memfabric",
        "use_layerwise": true
    }
}'
```

可将 D 服务端口设为 `8200`，便于与下面的 proxy 示例对应。先保留 eager 验证配置，跑通后再测试图模式。

### 5.2 P 节点配置

P 节点关闭 sparse KV offload，使用正常的完整 NPU KV cache，并配置：

```bash
--kv-transfer-config '{
    "kv_connector": "SfaRemoteD2HConnector",
    "kv_role": "kv_producer",
    "kv_port": 20050,
    "kv_connector_extra_config": {
        "transfer_backend": "memfabric",
        "use_layerwise": true
    }
}'
```

P 服务端口可设为 `8100`。P、D 使用相同模型权重和兼容的 KV 布局，使用互不冲突的 NPU 资源或不同节点。P 的 TP 必须大于等于 D 的 TP，且能被 D 的 TP 整除。

这里仅配置远程 KV 传输，验证 sparse offload 不要求额外启用 Prefill 的 AscendStore layerwise cache offload。

### 5.3 启动 proxy

P、D 服务就绪后，在目标服务器的仓库根目录运行：

```bash
python examples/disaggregated_prefill_v1/load_balance_proxy_layerwise_server_example.py \
    --host 127.0.0.1 \
    --port 9000 \
    --prefiller-hosts 127.0.0.1 \
    --prefiller-ports 8100 \
    --decoder-hosts 127.0.0.1 \
    --decoder-ports 8200
```

上述地址仅适用于 proxy、P、D 都能通过本机回环地址通信的情况。跨节点部署时替换为各节点可达 IP，proxy 的 host 也应为 D 可访问的地址，不能将 `0.0.0.0` 作为对外通告地址。

向 proxy 端口发送第 3 节的请求，即将请求 URL 改成：

```text
http://127.0.0.1:9000/v1/completions
```

所有服务的 `served-model-name` 应与请求中的 model 一致。只启动 D 服务并直接向 D 发送普通 prompt，不能完成这条 PD 验证流程。

`kv_port=20050` 是 D 控制端口基址。D 侧需要预留 `DP×TP` 个连续端口；P 不监听这些端口，而是通过请求元数据获得 D 的目标地址。

## 6. 验证顺序与结果记录

1. 单机 eager：确认初始化、prefill/decode、长请求及生成结果正常。
2. 单机图模式：与 eager 对比精度与延迟，覆盖多次 replay。
3. PD eager：确认 P 到 D 的 KV 传输及 D 上 CPU 池回载正常。
4. PD 图模式：验证完整路径的图回放与请求生命周期。
5. 固定模型、上下文、batch、TP 和 resident 容量，再记录命中率、KV H2D 数据量、decode 延迟及吞吐。

单机调试模式与 PD 分离模式的存储占用不同，不应混为同一内存容量基线。吞吐测试需在预热后进行，并明确是否开启 MTP、图模式与 prefix caching。

上述服务命令仍需在目标 NPU 环境执行。CPU C++ 策略测试不替代端到端精度与性能验证。

## 7. Reuse Prioritized LRU 对比测试

### 7.1 切换服务策略

在第 3 节启动命令的 `sparse_kv_offload_config` 内增加：

```json
"eviction_policy": "reuse_prioritized_lru",
"probation_age": 4
```

上述为需插入现有 JSON 对象的字段片段。完整示例：

```json
{
    "enable_sparse_sfa_c8": false,
    "sparse_kv_offload_config": {
        "enabled": true,
        "keep_device_kv_cache": true,
        "topk_buffer_size": 4096,
        "dram_size_per_dp_GB": 128,
        "lru_max_threads": 8,
        "eviction_policy": "reuse_prioritized_lru",
        "probation_age": 4
    }
}
```

与旧策略对照时设为 `"eviction_policy": "lru"`。`probation_age` 必须是 `[0,2147483646]` 内的整数，默认 4；P=0 不保证与旧 LRU 等价。新策略的 Hit age 归零、Miss age=P，未访问的有效槽饱和增龄；优先使用空槽，再淘汰最老的非 Hit 槽。

### 7.2 直接测试生产 C++ 决策代码

在仓库根目录执行：

```bash
python tests/ut/distributed/kv_transfer/sparse_kv_offload/test_lru_resident.py -v
```

该测试独立编译生产 C++ planner，不依赖 torch-npu、vLLM 或 NPU，仅需要 C++17 编译器。编译器支持 OpenMP 时启用多线程，否则打印 serial fallback 并验证串行路径。

测试包含随机参考算法对照、请求重置、后缀失效、age 饱和、空槽优先、重复索引和旧 LRU 行为回归。在构造的抗扫描序列中，预期对比结果为：

| 场景 | 原有 LRU 累计 Miss | Reuse Prioritized LRU 累计 Miss |
| --- | --- | --- |
| C=3、K=1，8 次访问 | 7 | 6 |
| C=4096、K=2048，6 轮访问 | 10240 | 8192 |

这些结果仅说明构造序列下的行为差异，不代表真实模型命中率或吞吐收益。测试还打印预热后的 CPU planner 调用耗时中位数（包含 ctypes 调用开销），不设置跨机器的固定耗时断言。

在完整开发环境中还可运行配置与 manager 测试：

```bash
pytest -sv tests/ut/test_ascend_config.py::TestSparseKVOffloadEvictionConfig
pytest -sv tests/ut/distributed/kv_transfer/sparse_kv_offload/test_sparse_kv_offload_manager.py
```
